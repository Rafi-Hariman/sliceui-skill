# SliceUI Handoff — portable project knowledge for a CLI-less agent

The main `/sliceui` pipeline assumes the agent can run `sliceui` commands. A web agent
(Microsoft Copilot custom agent, chat-only assistant) cannot: it only READS files the user
uploads, then writes code from a chat prompt + the pasted design image. Your job: produce
ONE markdown file — `.sliceui/handoff.md` — that carries everything that agent needs to
write code that reads as native to this project, with no CLI and no access to the repo.

You are writing for a reader with **no tools, no repo access, and no verify gate**. Every
fact it needs must be IN the file, in narrative markdown — never a JSON dump.

## Preconditions (stop if unmet)

1. `.sliceui/project-context.json` must exist. If it doesn't: tell the user to run
   `sliceui init` first, and STOP.
2. If `.sliceui/context/INDEX.md` or `.sliceui/conventions.json` are missing, the artifacts
   are stale — ask the user to re-run `sliceui init` before proceeding.

## Workflow

### Step 1 — Read the ground truth (in this order, targeted)

1. `.sliceui/context/INDEX.md` — framework, componentDir, profile, prefix, warnings.
2. `.sliceui/conventions.json` — `classVocabulary`, `ngDeepCorpus` (note which blocks are
   `reusable: true`), `componentAnatomy`, `naming`.
3. `.sliceui/context/capabilities.md` — library per element category (or read the
   `capabilities` key from project-context.json).
4. `package.json` — the ACTUAL framework version. Never guess a version; if INDEX and
   package.json disagree, package.json wins and you note the discrepancy.
5. **UII projects only** — if INDEX says `profile: uii`: read `.sliceui/uii-profile.md`
   (the action→authKey→icon table — it goes in verbatim), then GREP
   `.sliceui/pilar-reference.md` and `.sliceui/pilar-showcase.md` for the components the
   capabilities actually name (`uii-table`, `uii-pagination`, …) and read ONLY those
   sections. Never full-read those two files (54 KB + 184 KB).

### Step 2 — Verify against the real codebase (the step that makes this useful)

The CLI artifacts are Angular-first; on a Vue/React/Svelte/Tailwind project they can be
nearly empty — and the handoff must NOT be. You have Read/Glob/Grep; the web agent doesn't.
Use them:

1. Read 2–3 real components. Prefer the ones INDEX lists under samples; if that list is
   empty or Angular-shaped while the project is not, find them yourself:
   - Vue: `Glob src/components/**/*.vue` (also `src/**/*.vue` if empty)
   - React/Next: `Glob src/components/**/*.tsx`
   - Svelte: `Glob src/**/*.svelte`
2. From those files, extract the patterns a newcomer would need:
   - Component anatomy (SFC block order, script setup vs options, FC shape, runes).
   - File/folder naming convention (PascalCase vs kebab-case, index files, feature dirs).
   - How props/events/inputs are declared and wired.
   - **How styling actually works in this project** — the styling mechanism per framework:
     Angular → reusable classes + `::ng-deep` corpus (from conventions.json);
     Vue → `:deep(...)` blocks inside `<style scoped>`, `<style module>`, global stylesheets;
     React → CSS modules / styled / Tailwind composition — whichever the files show;
     Tailwind → the recurring utility composition patterns + theme tokens — v3: `tailwind.config.*`
     custom colors/spacing; v4 (CSS-first): `@theme` blocks in the project's `.css` — READ the css
     file, don't assume a config file exists. NOT a "class vocabulary" list.
   - Any store/composable/service pattern that repeats across the samples.
3. If the codebase contradicts the artifacts (e.g. conventions.json is empty but components
   clearly reuse classes), the CODEBASE wins and you say so in the file.

### Step 3 — Write `.sliceui/handoff.md`

First line: `<!-- Generated by SliceUI handoff (agent skill) — regenerate with /sliceui-handoff. -->`

Then this skeleton, in this order. Every section is REQUIRED — if a section has no content,
state `_(none detected — <what to do instead>)_` explicitly; never silently drop a section.

```markdown
> Generated <ISO timestamp> by the sliceui-handoff agent skill.
> Project knowledge captured <generatedAt from INDEX> (`sliceui init`).
> If the project changed since then, re-run `sliceui init` then /sliceui-handoff.

# Handoff — <Framework> <version> (for a CLI-less agent)

## How to use this file
2–3 lines: this replaces the project's JSON artifacts; the design is the image in the chat;
reproduce it exactly — this file says HOW this project writes that design.

## Project & framework
Framework + exact version (from package.json), module/standalone or composition/options,
componentDir (write target), styleExt, and the framework's syntax rules (the ones that
matter for codegen: e.g. Vue → <script setup lang="ts"> + <style scoped>; Angular 13 →
*ngIf/*ngFor, constructor DI, NgModule declarations — NEVER @if/@for/inject()/standalone).

## How this project writes components
The patterns from your Step-2 scan: anatomy, naming, props/events wiring, store/composable
usage. Cite the real file paths as provenance.

## Capabilities
Per category (select, table, modal, toast, date, pagination, …): the library this project
uses + a short usage snippet (≤ 6 lines). A null category is stated explicitly:
"not detected — use native HTML and flag it to the user." NEVER silently skipped.

## Styling system
Adaptive per framework (see Step 2): reusable classes / :deep blocks / Tailwind patterns +
tokens — whatever THIS project uses. Include the invisible effects (hover, open-state,
status colors, radius) with the exact code to reproduce them. Dedup near-identical blocks;
an oversized block gets its selector + effect summary + pointer to the source file.

## Page anatomy & naming
Only what was actually detected (table skeleton, pagination floor, selector/component
prefix, event-handler naming). Omit honestly if none.

## Design tokens
The frequently-used ones (colors/theme first), capped ~20. The full-list pointer must name
the VERIFIED source — never an assumed one:
1. Read `.sliceui/context/design-tokens.md` first. Point to it ONLY if it actually contains
   tokens (a file saying `_(none detected)_` is empty — it is not a source).
2. If it is empty but your Step-2 stylesheet scan found tokens (Tailwind v4 `@theme` blocks,
   CSS custom properties in a plain `.css`, or any pattern the old scan missed), point to the
   stylesheet file you ACTUALLY read, naming the path explicitly — e.g. `full list:
   src/assets/main.css`.
3. If the artifact is empty AND your scan found nothing: write
   `_(none detected — use the design's exact values)_` with no pointer at all.

## Org component grammar   (UII projects ONLY — omit the whole section otherwise)
The action→authKey→icon table VERBATIM, plus the pilar wiring for the components the
capabilities name. Non-UII projects never mention pilar/uii components.

## References (writing samples)
Pointers only — real file paths, golden references marked READ FIRST. Samples teach
wiring, never structure to copy.

## Aturan untuk Agent Tanpa CLI
The five invariants below, rewritten by you in the target framework's own terms.
```

### The five invariants (the payload of the last section)

Write these as numbered imperatives, EACH translated to this project's framework — not as
Angular boilerplate. Then close with: "There is no `sliceui verify` gate available to you —
a human must review your output against the design. State plainly that the gate has not run."

1. **Reproduce only what the design shows.** No invented structure, wrappers, or elements.
2. **Style the way this project styles.** Reuse its classes/patterns from the sections
   above — in a Tailwind project that means composing the established utilities, not
   inventing CSS classes; in an Angular project it means the exact classVocabulary members.
3. **Copy the invisible effects.** Hover/open-state/status/radius effects are not visible
   in the design image — they live in the styling-system section; without them the UI is wrong.
4. **All data is mock.** Mark it `// TODO: wire to <service>` (or `<!-- mock data -->`).
   Never guess an API shape or endpoint.
5. **Text is literal from the design.** No translation keys, no i18n wrapper — slicing is
   mock code, not production i18n.

## Compactness rules

- Target ≤ ~20 KB. This is a chat attachment, not an archive.
- Dedup near-identical blocks (same body, different selector) into one + "(+N variants)".
- Samples teach the PATTERN — quote ≤ 6 lines, never dump a component body.
- NEVER wrap raw JSON in a code block as "content". Narrative + short snippets only.
- A null capability is stated, never hidden. A missing org profile omits the org section
  entirely — never emit pilar/uii vocabulary for a non-UII project.

## Anti-patterns

- **Never** invent a library the project doesn't have. Null → native + flag.
- **Never** copy a sample component's structure/wrapper — samples teach wiring only.
- **Never** use another framework's mechanism in the file ("::ng-deep" in a Vue project,
  "class vocabulary" in a Tailwind project, `@if` in an Angular ≤16 project). Write in the
  target framework's own terms throughout.
- **Never** imply verification happened. The web agent has no gate; the file must say so.
- **Never** include org-private (pilar/uii) content unless `profile: uii` was detected.
- **Never** point to a file as the source of a fact without having READ that file in this
  session. Every "full list: …"/"see `<path>`" claim in handoff.md must be verified against
  the pointed-to file's actual content — not assumed from its name. If the fact came from
  your own codebase scan (e.g. tokens in a stylesheet the scan artifact missed), the pointer
  names THAT file. A pointer to an empty artifact is a false claim.

## After writing

Report to the user: the output path, the file size, what you scoped OUT (target mode?
sections with no detected content?), and any discrepancy you found between the CLI
artifacts and the real codebase.
